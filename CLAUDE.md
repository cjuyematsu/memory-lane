## Expo SDK 56 — read the versioned docs first

Expo and React Native APIs in this project are **SDK 56 / RN 0.85 / React 19**, which differ substantially from older releases you may recall. Before writing code against any `expo-*` package, `react-native`, `expo-router`, or `react-native-reanimated`, consult the exact versioned docs at https://docs.expo.dev/versions/v56.0.0/. Do not rely on memory of older Expo APIs (e.g. `expo-file-system` here uses the `File`/`Paths` object API, not the legacy `FileSystem.*` functions).

Day-to-day development is `npx expo start` against an already-installed dev build. This app uses a custom native build (a patched `expo-media-library`, background location, notifications), so it **cannot run in Expo Go**. The native app is built **in Release configuration on a physical device** (iOS: `--configuration Release --device`; Android: `--variant release --device`): the core background-location / geofencing and notification paths need a real device and only behave like production under a Release build — not the simulator or a debug build. Rebuild after changing `app.json` plugins/permissions or the patch.

`postinstall` runs `patch-package`. The patch in `patches/expo-media-library+56.0.6.patch` does two things: (1) adds Android video GPS extraction (`MediaMetadataRetriever`, in both `AssetLegacy/ModernDelegate.kt`) so videos can be located, and (2) sets `isNetworkAccessAllowed = true` in iOS `UriExtractor.swift` so `getUri()` can resolve iCloud-offloaded originals (without it, raw share fails for any "Optimize iPhone Storage" photo/video). Don't `npm install` a version that drops these without re-checking the patch applies. When regenerating with `npx patch-package expo-media-library`, **always pass `--include 'AssetLegacyDelegate\.kt$|AssetModernDelegate\.kt$|UriExtractor\.swift$'`** — a bare run sweeps in 1MB of leaked `android/.gradle` build junk.

SDK 56 installs Expo pods as **precompiled binaries**, and `npx expo install`'s `~` ranges float patch versions — so a newly added package's prebuilt framework can be compiled against a **newer `expo-modules-core`** than this project's (pinned by the `expo` version). The app then **builds clean but dies instantly at launch**: dyld "Symbol not found … Expected in: ExpoModulesCore.framework", signal 6 — looks like "opens and immediately closes", leaves no crash dialog, and no compile-time check can catch it. Diagnose with `xcrun devicectl device process launch --console --device <id> com.uyeyu.memorylane` (device must be unlocked). Fix: add the package to `expo.autolinking.buildFromSource` in package.json so it compiles against the local core (this is why **expo-camera** is listed there alongside the patched expo-media-library), then pod install + rebuild.

`patches/expo-image+56.0.9.patch` (iOS, regenerate with a plain `npx patch-package expo-image`; rebuild required) makes `ph://` loads **two-tier**: `PhotoLibraryAssetLoader.swift` uses `.opportunistic` delivery + `.exact` resize and Gaussian-blurs the degraded first delivery (blur→sharp focus-in); a **failed FINAL delivery falls back to the best LOCAL rendition** (no-network re-request, delivered sharp as final — Apple-Photos parity on a full/offline phone, since PhotoKit serves third-party apps the same local device-optimized versions Photos shows) and emits a **real `onError` only when nothing local exists** (cancellations stay silent — erroring them would mark a recycled cell's new asset unreachable); `ImageView.swift` renders non-finished images, runs the dissolve only when replacing an already-shown frame, and adds **`isPlaceholder` to the `onLoad` payload**. The JS invariant that falls out: **the blur fires `onLoad` too** — anything meaning "the bytes are here" (recovery-timer disarm, warm-queue marking, download accounting) must check `isPlaceholderLoad` (`lib/image-load-event.ts`, the only place the untyped field is read) or use `use-icloud-image-load`'s `imageReady`-vs-`preview` tiers; treating the blur as loaded is how "stuck on a blur forever with no Retry" happens. The mounted-view path requests screen-sized pixels; the **prefetch path has no view context and fetches full-res** — never `Image.prefetch` a `ph://` URI (the feed's hidden warm layer / mounted neighbors are the prefetch mechanism). The warm layer serializes iCloud downloads to one at a time (`lib/feed-warm-plan.ts`), and a **failed** warm download pauses that slot (`WARM_FAILURE_PAUSE_MS`) — dropping a failed entry triggers an immediate refill, so without the pause a fast-failing condition (offline, storage-full) loops mount→error→drop→refill against the Photos framework all session.

`patches/expo-camera+56.0.8.patch` (iOS, regenerate with a plain `npx patch-package expo-camera`; rebuild required) makes `pictureRef: true` an actually-fast shutter path — upstream it still ran the **full JPEG encode then re-decoded the result** (only the file write differs, so the retake shutter stalled ~2s; `skipProcessing` doesn't exist in the iOS native options at all): (1) `CameraPhotoCapture.swift` early-returns `PictureRef(takenImage)` right after the crop, skipping the encode+re-decode AND `normalizeOrientation`'s full-size redraw — safe because every consumer honors the UIImage orientation flag (UIKit/expo-image rendering, ImageManipulator fixes orientation on load, `saveImage` normalizes before encoding); (2) pictureRef captures use `.speed` quality prioritization and the **smallest `supportedMaxPhotoDimensions`** of the active format (12MP-class, not 24/48MP); (3) `ExpoCameraUtils.saveImage` adds `result["uri"]` — unpatched iOS returns the path only under `url` while the JS `PhotoResult` type (and Android) say `uri`, so `savePictureAsync().uri` is undefined. Also upstream: Android `savePictureAsync` floors fractional quality to 0 (`quality.toInt() * 100`) — never pass a quality option to it (JS guards both quirks in `recreation-camera.tsx`).

`patches/expo-modules-jsi+56.0.7.patch` (iOS, rebuild required — the package always compiles from its Swift sources via a podspec script_phase, so unlike precompiled expo-modules-core it IS patchable) fixes a hard crash (SIGTRAP, uncatchable from JS) when a **shared object is passed to an `Either`-typed native argument**, e.g. `ImageManipulator.manipulate(pictureRef)` — the retake camera's front-selfie un-mirror. `DynamicEitherType` probes each branch with `try?`, but the URL branch's `Convertible` cast calls `JavaScriptValue.getAny()`, which recurses into the shared object's enumerable properties and hits `FatalError` on its **methods** (function values) instead of throwing. The patch makes `getAny()` skip function/symbol/bigint property values (like it already skips undefined), so the URL cast throws normally and the Either falls through to the `SharedRef<UIImage>` branch. Regenerate with `npx patch-package expo-modules-jsi --include 'JavaScriptValue\.swift$'` — but first move `apple/{.build,.DerivedData,Products}` out of the package (patch-package dies on a symlink in `.build` even with `--include`), then move them back.

`patches/expo-task-manager+56.0.15.patch` (iOS, regenerate with a plain `npx patch-package expo-task-manager`; rebuild required) fixes a real field crash (confirmed via a `.ips` pull off the phone, 2026-07-22): `EXTaskService`'s `_events`/`_eventsQueues` NSMutableArrays are mutated from **multiple threads with no synchronization** — `executeTask` appends on the location-delegate/main thread while the JS task-finish (`notifyTaskWithName`, via `TaskManagerModule`) removes on `expo.modules.AsyncFunctionQueue`. Concurrent mutation corrupts the array and `removeObject:`'s `isEqual:` walk traps (SIGTRAP in `__StringStorage.isEqualToString`, ~seconds after a launch that coincides with geofence task activity). The patch wraps every `_events`/`_eventsQueues` access in `@synchronized (_events)`. Pull native crash reports anytime with `/tmp/pmd3/bin/pymobiledevice3 crash pull <dir> -m "PastPic"` (venv recipe in auto-memory).

**Sentry crash reporting**: `@sentry/react-native` (plugin in app.json, metro wrapped with `getSentryExpoConfig` — both preserve the svg-transformer config). `lib/sentry.ts` holds the DSN (**live** since the TestFlight soak; an empty string fully disables) and `initSentry()`, which `_layout.tsx` calls **before** `initCrashReporting()` — crash-log's ErrorUtils handler delegates to the previous handler, so this order means fatals land in the on-disk log AND Sentry. Rejections + boundary errors reach Sentry via `setCrashForwarder` (crash-log never imports the SDK, keeping tests clean). Release-only (`enabled: !__DEV__`), no PII/replay/tracing per the privacy posture. Source-map upload needs org/project added to the app.json plugin entry + `SENTRY_AUTH_TOKEN` (EAS secret). Native module → rebuild required.

Pre-release: run the on-device scenario matrix in `docs/battle-test.md`; corrupt-file resilience is automated in `src/lib/__tests__/persisted-parsers-fuzz.test.ts` (every persisted parser vs a shared hostile corpus).

**Demo mode** (`lib/demo-mode.ts`, shoot plan in `docs/demo-video.md`): a persisted lat/lng override for filming the launch video, since a real geofence notification needs you standing at an old-photo place that isn't routine and isn't in cooldown. Nothing is faked but the coordinate — every gate in `handleClusterEnter` is keyed on the *cluster's* position, so a teleported app passes them all on their own merits and the notification/tap/cooldown paths are the real ones. Every position read in the app goes through `getPosition`/`getLastKnownPosition` (the five `Location` call sites; `watchPositionAsync` is deliberately untouched). Gated on **`process.env.EXPO_PUBLIC_DEMO === '1'`**, inlined at build time — a store binary built without it can't carry demo mode, and a stale `demo-mode.json` is ignored (this replaced a hand-flipped `DEMO_BUILD` constant; battle-test row 34 verifies it). Reached by long-pressing the Settings privacy note. `parseDemoMode` collapses to off unless the coordinate is finite and in range — a NaN would reach `distanceMeters` and make every radius comparison false.

## What this app is

"PastPic" surfaces old photo memories tied to **place**. Its core feature: while you move around, it geofences clusters of locations where you took photos long ago and notifies you when you return to one — then shows those photos. Two tabs:
- **Camera Roll** — a shuffle feed of single framed photos (`components/feed/`).
- **Near Me** — a grid of photos/videos taken within a radius of your current location (`components/near-me/`).

## Architecture

### The shared located-assets index is the spine
`hooks/use-located-assets.ts` is the single source of truth that everything else derives from. It performs the one expensive operation in the app — a native metadata read (GPS + creation time + media type) per asset — and builds an `AssetIndex` that is:
- **persisted to disk** (`located-assets.json` in the document directory) and reused across launches,
- **updated incrementally**: on library change only newly-added assets are located and deleted ones dropped (`sync()`), never a full re-scan. A thrown/timed-out locate resolves `{kind:'failed'}` and is **left out of `processedIds`** so the next sync retries it (a `none` = successfully read, no GPS, is processed); recording failures as no-GPS was silently dropping photos from Near Me/clusters for good,
- **cached in a module variable** keyed by the asset-array reference, with in-flight dedup.

Two consumers derive cheap in-memory results from it:
- `hooks/use-photo-clusters.ts` — quantizes located assets into ~50m grid cells (`PhotoCluster`). Cluster cache is keyed on the `AssetIndex` object reference, so it auto-recomputes whenever the index rebuilds.
- `hooks/use-nearby-assets.ts` — radius query for the Near Me grid (wider net: 500m photos / 1km videos vs. the ~50m cluster cells).

When touching anything location/photo-related, work through this index rather than re-reading metadata.

### Background geofencing & notifications (the hard part)
`lib/geofence-manager.ts` defines the `TaskManager` task and all geofence lifecycle logic. Critical constraints:
- It is **imported first in `app/_layout.tsx`**, before anything else, so `TaskManager.defineTask` registers before the OS can cold-launch the headless task (otherwise RN throws "No task registered").
- The task may run **headless with the app killed**, so its handlers read everything from disk (`loadSettingsFromDisk`, `loadClustersFromDisk`) and never touch React or in-memory module state that wouldn't exist in a cold background process.
- Platforms cap region monitoring at ~20 regions. When there are more notifiable clusters than slots, the last slot becomes a **re-anchor boundary**: an exit-only region whose exit wakes the task to re-pick regions around the user's new position — background rotation without continuous tracking.
- **Foreground fallback**: with only When-In-Use location (no "Always"), `startGeofencingAsync` throws. The manager then runs a foreground `watchPositionAsync` that pushes hits through the same enter pipeline. The "Always" upgrade is only requested when the user enables Memory notifications, not at onboarding.
- **Android Auto Backup is OFF** (`app.json` `android.allowBackup: false` — a manifest change, rebuild required). With it on, an uninstall/reinstall silently restored `files/` (onboarding "completed", settings `enabled:true`, the index) **and native SharedPreferences** (expo-task-manager's registered geofence task, expo's asked-permissions cache) while runtime permissions reset — the restored task then auto-started at boot and fired a no-gesture permission request Android filters and never answers (logcat signature: `V/Activity: No requestable permission in the request.`), wedging every later `getPermissionsAsync` so the feed sat on the Polaroid forever with onboarding skipped. Two in-app guards remain for devices already in that state: `useMediaPermission` publishes a not-granted fallback when all retries fail (locked screen, never an endless Polaroid), and the orchestrator degrades `enabled` to off + `unregisterAllTasksAsync` when notif AND background-location permissions are both confirmed missing (`lib/notification-degrade.ts`, pure + unit-tested; unknown/timed-out reads never degrade).

`components/notifications/notification-orchestrator.tsx` is a renderless component that drives this from React: gated entirely on the `enabled` flag, evaluates geofences on app foreground, and routes notification taps to the Near Me cluster view.

The notification gating pipeline (in `handleClusterEnter`): `enabled` → `isAreaNotifiable` (cluster's newest photo older than ~90 days **and** no recent media anywhere in a 150m neighborhood) → **routine-place suppression** (`lib/place-presence.ts`) → **per-cluster cooldown** (`lib/cluster-cooldown.ts`, keyed by the cluster's stable grid-cell id — once a place surfaces its memory it's "spent", so that exact spot stays quiet even as you keep passing through; distinct nearby places aren't silenced. The window is **user-configurable** (`placeCooldownMs` in `use-notification-settings.ts`; options/`describeCooldown` in `lib/place-cooldown.ts`; the `CooldownPicker` shows it in the onboarding "Remind me again" step + the Settings sheet): default ~90 days, down to 1 day, or `null` = "Only once" / silenced forever. `isClusterInCooldown`/`markClusterNotified` take the window; `handleClusterEnter` passes `settings.placeCooldownMs`) → **location cooldown** (`lib/notification-cooldown.ts`, 12h within a ~100m density-adaptive quiet zone — only dedupes near-duplicate clusters on a single arrival; the long-term "don't repeat" job lives in the per-cluster cooldown). The routine gate is the real home/work silencer: every enter logs a presence ping (`recordPresence`), and `isRoutineLocation` mutes a spot once you've been there on ≥3 distinct days inside a rolling 14-day, 150m window — so home/work/gym go quiet after ~2 days and *resurface* when you stop coming (move out / change jobs). It replaced an old tap-engagement scheme. The greeter (below) records presence too, so the signal works even with notifications off. Foreground notifications are suppressed at the system level (`setNotificationHandler` returns all-false) and shown as an in-app banner (`lib/foreground-banner.ts` → `components/notifications/memory-banner.tsx`) instead — the foreground banner shows the **Near Me count** (`nearbyCount` over the in-memory index at the cluster center, NEARME_OPTS radius — *not* the single ~50m cell, so the number matches the Near Me grid) and taps to the Near Me grid via `requestNearMe` (which now also refreshes it), never the ClusterView. The **background** OS notification still opens the ClusterView on tap (orchestrator → `setPendingCluster`). The location cooldown is a `createLocationCooldown({file,windowMs,radiusM})` factory (`lib/location-cooldown.ts`); the geofence one is the 12h instance. **Those radii are no longer fixed**: `lib/relevance-radius.ts` (`relevanceRadiusFor` = ½ the distance to your k-th=2 nearest *other* cluster, clamped) makes the geofence trigger, the `isAreaNotifiable` suppression neighborhood, the cooldown radius, and the Near Me grid (`computeNearby`'s `radiusM`) all adapt to local photo-cluster density — tight in dense cities, wide at a spread-out beach. Floors keep dense areas tight (the geofence floor is the ~120m iOS region-accuracy limit, so the OS trigger only widens; in-app checks can also tighten); a hard **250m ceiling caps every notification radius** (TRIGGER/SUPPRESS/COOLDOWN_OPTS) so even a lone memory in an empty area pings ~a couple blocks away, not the old quarter-mile (400m felt far/random). `NEARME_OPTS` (the Near Me grid, not a notification) is the one radius still above that, at 300m. `isInCooldown(lat,lng,now?,radiusOverride?)` takes a per-call radius.

Separately, `components/notifications/nearby-memories-greeter.tsx` (root-mounted, renderless) shows a **"N memories near you" banner on every app open** (cold launch + each foreground), independent of the notifications toggle — it only needs photo+location. It reuses the same single `BannerData` slot (one `'nearby'` shape, now shared with the foreground geofence banner, so the two never stack), counts all Near Me items (150m), has its own 24h `nearby-greeting-cooldown` (same factory), is suppressed at routine places (`isRoutineLocation`, same home/work gate as notifications) and records presence on every open, and taps to the Near Me grid via `lib/near-me-request.ts` (`requestNearMe` switches the tab **without** opening a ClusterView, unlike `setPendingCluster`). Pure decision in `lib/nearby-greeting.ts` (`shouldGreet`).

### Cross-tree state: hand-rolled pub/sub, not a state library
There is no Redux/Zustand/Context for shared state. The recurring pattern is a **module-level variable + `Set` of subscribers + a `useXxx` hook** that subscribes. See `lib/pending-cluster.ts` (bridges out-of-React notification listeners to the UI), `hooks/use-notification-settings.ts`, and `hooks/use-asset-feed.ts`. When adding shared state, follow this pattern: a `loadFromDisk`/`save` pair, a module cache, an in-flight promise to dedupe, and a subscriber set.

### Persistence
`lib/persisted-file.ts` wraps the SDK 56 `File`/`Paths` API. All durable state (the index, notification settings, cooldown, engagement) lives in the **document directory** (`Paths.document`) — not cache, which the OS purges under storage pressure — and `readPersisted` does a one-time migration from the legacy cache location.

### Navigation
Uses `expo-router` but with a **single route** under `src/app/`: `_layout.tsx` (root providers + global overlays) and `index.tsx`, which just renders `components/top-tabs.tsx`. `TopTabs` is a custom **gesture-driven three-pane pager** (Reanimated + RNGH, row `width×3`, offsets `0 / -w / -2w` via `tabOffset`), not expo-router navigation — it manages the **Camera Roll / Near Me / Recreations** swipe (the UI labels are **MEMORIES / NEAR ME / RETAKES** but the internal ids stay `cameraRoll`/`nearMe`/`recreations`; `tabPan` steps one pane per swipe and clamps to the ends), the memory-feed overlay that slides over, and gates tab-swiping so you can't escape an open memory/photo/recreation view. The tab bar positions labels **explicitly from measured text widths**: MEMORIES anchored `BAR_EDGE_MARGIN` (14) from the left edge, NEAR ME locked to the exact screen center, RETAKES anchored 14 from the right edge (space-evenly is only the pre-measurement first-frame fallback). The user settled on this left/center/right anchoring after rejecting centered-cluster, equal thirds, and plain space-evenly — it reads balanced because the words are **deliberately near-equal width** (MEMORIES/NEAR ME/RETAKES), so don't rename a tab to a much longer/shorter word without rechecking the balance. Inactive labels dim; a **label-width ink underline** slides + stretches between `onLayout`-measured label centers/widths by reading `tabX`, so it tracks drags and tap animations with no extra state. The **Recreations** pane is `RecreationsGallery` (see the recreation section); it reports viewer-open up via `onViewerOpenChange` (like Near Me) so the pager freezes while a recreation is open. Background OS-notification taps flow through `pending-cluster` → TopTabs switches to Near Me → `ClusterView` overlay; the foreground in-app banner instead flows through `near-me-request` → Near Me grid (refreshed, no ClusterView).

### First-run onboarding (`components/onboarding/`)
Replaces the old rapid-fire boot prompts (the deleted `lib/onboarding-permissions.ts`). `useOnboardingStatus()` (`hooks/use-onboarding-status.ts`) returns `'deciding' | 'active' | 'done'` from a persisted `{completed}` flag (`hooks/use-onboarding.ts`, same pub/sub pattern as notification settings, `onboarding.json`); `_layout.tsx` **withholds the whole app** (`<Slot/>` + the greeter) until `'done'` and renders `OnboardingFlow` while `'active'`. Withholding is load-bearing, not cosmetic: a live Near Me mounted under the overlay re-requests location on the AppState 'active' that fires when an OS dialog dismisses, so leaving it mounted pops the location prompt mid-onboarding. `OnboardingFlow` is a **tap-through** tour (welcome → privacy → Camera Roll → Near Me → Memory notifications → Always-location → done) that **primes each permission with an explanation + a rich mock of that screen** (`mocks.tsx`) before surfacing the OS dialog: photos via `ensureMediaPermission`, When-In-Use via `requestForegroundPermissionsAsync`, notifications via `Notifications.requestPermissionsAsync`, and the **"Always" location upgrade on its own dedicated page** via `requestBackgroundPermissionsAsync` (each permission gets its own page; bundling the Always ask onto the notifications tap surfaced a scary "permanent location" prompt). The notifications step enables the feature when notif+foreground are granted and routes to the Always page; declining notifications skips it. Each ask **advances regardless of the answer** (denials handled by the existing in-app locked screens). **Resilient to a mid-flow kill:** the persisted state is `{completed, started, step}` — the flow writes `started:true`+`step` on every step (`saveOnboardingProgress`), so a relaunch resumes at the same step. Migration (auto-complete for installs predating onboarding that already have photos) is gated on **`!started`** (`lib/onboarding-decision.ts`, pure + unit-tested) — so granting photos then closing no longer skips the rest of onboarding; only a true upgrader who never saw the flow is migrated. `restartOnboarding()` (resets to step 0) still exists to re-show the tour, but is no longer surfaced in Settings — the "How PastPic works" row was replaced by a **Permissions** row. The Settings sheet is opened from a **gear pill on the Retakes tab** (`recreations-gallery.tsx`, lower-right) — moved off Near Me so that tab has no floating controls; Retakes is effectively the profile/"you" tab, the conventional home for settings. It is a single Modal that swaps **in place** between its main list and a `PermissionsPanel` sub-view (`components/notifications/permissions-sheet.tsx`) via a `view` state (a Modal-over-Modal doesn't reliably present on iOS — don't nest them); the panel is **informational** — it lists all five permissions (Photos/Camera/Location While-Using/Location Always/Notifications) with a live status dot (refreshed on mount + `AppState` 'active') and a **single "Open Settings" button** (per-row buttons all deep-linked to the same OS page, so there's just one). The sheet resets to the main view on reopen via the set-state-during-render "reset on prop change" pattern (not a setState-in-effect).

### Sharing a surfaced photo (`components/share/`)
Share buttons in the feed (bottom-left, mirroring shuffle) and the Near Me viewer top bar call `requestShare(asset, isVideo)` (`lib/share-memory.ts`, the same module-pub/sub pattern as `pending-cluster`). The root-mounted `ShareHost` shows a gallery-themed chooser, then runs one of two flows. **Raw** (`prepareRawShare` → `asset.getUri()` gives the original `file://`; offloaded iCloud originals are **downloaded** thanks to the `UriExtractor.swift` patch above — the prepare step is wrapped in `withTimeout(…, RAW_SHARE_TIMEOUT_MS)` so a slow/offline download can't hang the spinner, surfacing a friendly iCloud error) → `Sharing.shareAsync`. For **iOS photos** the original is first **copied (same bytes/format) into `Paths.cache`** and that copy is shared: iOS builds the share-sheet thumbnail out-of-process and can't read the Photos-managed `fullSizeImageURL`, so sharing it directly shows a blank preview — a file in our sandbox previews correctly. Videos preview fine from the original URL and are shared as-is (no large copy). Note `expo-sharing` **ignores the `mimeType`/`UTI` options on iOS** — the preview comes purely from the file. **Framed** (photos only) mounts an **off-screen** `ShareCard` that **reproduces the Camera Roll feed card** (3:4 `PhotoRatio` frame, photo cover-cropped to fill it / contain+letterbox for landscape, same date/place caption) onto a **fixed 1080×1920 (9:16) `STORY_CANVAS`** (`share-memory.ts`) — so a shared memory looks exactly like the feed, minus the floating share/shuffle buttons, sized for IG Stories/Reels + TikTok. `SHARE_LAYOUT` fractions = the feed's absolute px ÷ the ~393pt feed width; the block is lifted slightly above center (`liftFrac` bottom-padding). (A Story/Post/Square picker, and an aspect-preserving layout, were both tried and dropped — 4:5/1:1 and letterboxing made the photo look small.) The pure `computeShareFrame` fits the 3:4 box to the canvas; all metrics are fractions of the canvas so it's identical at any resolution. The card is laid out at `canvas.width / PixelRatio.get()` **logical** points so view-shot's native-scale capture lands at ~1080px **without** passing `width`/`height` to `captureRef` (that resize path can blank on the New Arch). Waits for its `onReady` (image decoded + caption settled), then `captureRef` (react-native-view-shot) → `shareAsync`. Off-screen = `left:-10000` and **opaque** — `opacity:0`/`display:none` makes view-shot capture blank. If a framed capture ever blanks on the New Arch, try captureRef's iOS `useRenderInContext: true`. `asset.getInfo()` (this is the SDK 56 **MediaLibraryNext** `Asset` API) has **no `localUri`** — use `getUri()` for a file path. Both deps are native → a rebuild is needed.

### Photo recreation (`components/recreate/`)
Retake an old photo at its spot: camera-with-ghost → review (Retake / Share / Save, **nothing auto-saves**; X discards the capture) → optional gallery. **Save does not close the review** (the button just shows "Saved"; changing the mode/primary re-arms it) — only X/back closes, so you can save then also share. Entry points: a center camera button in the feed's button band (photos only — gated on `useAssetMetadata(currentAsset)`, the *reactive* hook, because a bare `getCachedMetadata` read in render is the React-Compiler stale-memo trap) and the Near Me viewer top bar; both call `requestRecreation({asset, creationTime, location})` (`lib/recreation-request.ts`, pub/sub). The root-mounted `RecreationHost` (`_layout.tsx`, after `<Slot/>`, before `MemoryBanner`/`ShareHost` so the share Modal stays on top) renders the flow full-screen and unmounts entirely on close (one live `CameraView` max); TopTabs gates `tabPan.enabled` on it *and* on `recreationsViewerOpen` (RNGH receives touches under overlays on Android). The camera (`recreation-camera.tsx`, expo-camera, permission asked **contextually on first use**, never at launch/onboarding; AppState recheck unlocks after a Settings grant) clips the preview to the feed's 3:4 `frameLayout` box — portrait 4:3 sensor ≈ uncropped preview, so ghost alignment is WYSIWYG for the capture and the diptych — with the old photo as an opacity-cycled `ph://` `<Image>` on top and a **soft** distance hint (`formatDistanceHint` in `utils/distance.ts`; `useCurrentLocation` never prompts). The shutter captures via **`takePictureAsync({ pictureRef: true })`** + the expo-camera patch above — the ~2s shutter stall was the full-res JPEG encode(+re-decode) inside the native capture path, which unpatched runs **even for pictureRef**; the patch is what makes the ref path fast. `CapturedPhoto` carries the native `ref` (renders directly in expo-image for the review preview; the front-camera un-mirror flips the *ref* via `ImageManipulator.manipulate(ref)`) plus `fileUri()`, a memoized background `savePictureAsync` started at capture — Save/Share/`addRecreation` await it (plain uri data stays the persistence/share boundary). Don't "fix" capture latency with `pictureSize` on iOS: mid-res presets are all 16:9, which breaks the 3:4 WYSIWYG. TS note: the shared-ref *instance* type is `SharedRefType<'image'>` from `expo` (`SharedRef` there is the constructor type — using it demands `prototype`). Kept pairs live in `recreations.json` + a `recreations/` dir under `Paths.document` (`lib/recreations.ts`): store **filenames, never absolute URIs** (the iOS container UUID changes across updates; resolve via `recreationUri`), and `addRecreation` copies the jpg **before** writing the JSON row (crash leaves an orphan file, never a dangling row). A recreation whose original was later deleted **degrades** (Letterbox "no longer in your library" panel in tiles/preview/card), never crashes and can still re-share. Share goes through `requestThenNowShare` → `ShareTarget` is a `kind: 'asset' | 'thenNow'` union; the thenNow chooser offers two `ThenNowCard` variants (BeReal-style: primary photo + white-bordered corner inset via pure `computeThenNowInset`; `primary` is user-swappable and persisted): **'clean'** (default — the 1080×1440 photo itself with a small on-photo date+distance chip) and **'framed'** (the 9:16 story canvas + caption, same `computeShareFrame` composition as ShareCard). The payload is **plain persisted data, not an `Asset`** (gallery re-share must outlive caches and the original), including `capturedDistanceM` measured at shutter time. Save (BOTH mode) writes the clean composite to the camera roll via `useCompositeCapture` (off-screen capture, same view-shot rules) AND keeps the pair in the gallery; the camera sheet swipe-down-dismisses (camera phase only — a stray swipe on review would discard an unsaved capture). **Capture-grade `onLoad` gates on `!isPlaceholderLoad(e)`** in both ShareCard and ThenNowCard — capturing the blur ships a blurry export; the patch's local-rendition fallback guarantees a final, and the host's `CAPTURE_TIMEOUT_MS` is the bail-out. Gallery (`recreations-gallery.tsx`): the **Recreations pane** — the third tab of the TopTabs pager, not a Settings row or overlay (an earlier slide-up/swipe-down-dismiss overlay reached from Settings was replaced). It pads its grid under the bar with `frameTop(insets.top)` (same as Near Me), is a 2-col FlashList (no `recyclingKey`, per the grid's rules; tile failure state keyed by record id so recycling can't leak it) → viewer with re-share / `Asset.create(uri)` save-to-roll / delete, and reports viewer-open up via `onViewerOpenChange` so TopTabs freezes the pager. RN 0.85 types have no `StyleSheet.absoluteFillObject` — write the explicit position fields.

### Near Me is a frozen snapshot, not a live list
The grid renders a **snapshot** (`displayItems` in `near-me.tsx`), not live `items`. It updates only on (1) first load, (2) app foreground (`AppState` 'active'), and (3) explicit user refresh (pull-to-refresh + the empty-state button, both routed through `onUserRefresh` — Near Me has **no floating refresh pill or settings gear**; both were removed to declutter). Passive library changes (a photo taken/deleted while the app is open) do **not** alter the grid — by design, so nothing pops in/out under the user. Mechanism: an `accepting` window (opened by `arm()`, closed by a token-guarded `SETTLE_MS` timer) during which a **guarded set-state-during-render** (`if (status==='ready' && displayItems!==items && (accepting || displayItems===null)) setDisplayItems(items)`) adopts each settled recompute; outside the window it's inert. Do **not** convert this to a `setState`-in-`useEffect` (trips `react-hooks/set-state-in-effect`, React 19). **Critical:** `useNearbyAssets` is still fed **live** `assets`/`origin` — never freeze its inputs, because it drives the shared global located index (`ensureIndex`) that the geofence notifications read; freezing inputs would drop new photos from the on-disk index. The notification orchestrator (root-mounted, own `useAssetFeed`) is unaffected and keeps the index/clusters current independently. `useCurrentLocation` is one-shot (updates on foreground/`refresh`), so walking never churns the grid anyway.

The identity-stability layers below still matter (they keep the live `useNearbyAssets`→`items` pipeline cheap and stable, which the snapshot copies from):
The dominant Near Me flicker was **data churn, not the list widget**: `addListener` MediaLibrary events fire constantly (iCloud sync, edits), each making `use-asset-feed` republish a new `Asset[]`, which makes `computeNearby` mint all-new `NearbyAsset` objects, so the grid received new data and **repainted every tile**. Swapping FlatList→FlashList didn't help because the churn is upstream. Fixed by **identity stability at three layers**, all keyed on the data, not the widget — keep these when touching Near Me:
- `use-asset-feed.ts` `sameAssetIds` — skip `publishAssets` when the reloaded library has the same ordered ids (don't hand out a new `Asset[]` for a no-op event).
- `use-nearby-assets.ts` `stableNearby`/`sameNearby` — reuse `NearbyAsset` objects by id so unchanged tiles keep their reference across recomputes.
- `near-me.tsx` — `items` is a signature-memo (stable array ref while the ordered nearby-id list is unchanged), `onPressItem` is `useCallback`, and `Grid` is `memo` — so a NearMe re-render can't repaint the grid.

The grid (`grid.tsx`) is **FlashList v2** (`@shopify/flash-list`, JS-only, no native rebuild; needs the New Architecture, which SDK 56 has) for smooth scroll recycling, with `maintainVisibleContentPosition` **disabled** (it's on by default in v2) so a newly-taken photo lands at the top of the viewport rather than anchored above it.

On `expo-image`'s **`recyclingKey`**: changing it resets the image to blank/placeholder before loading. The grid tiles **deliberately do NOT set it** and cross-dissolve (`transition={180}`) instead — because the list is newest-first, a single add/delete shifts every item by a slot, the recycler hands each visible cell a new `item`, and with `recyclingKey` set the whole grid would blank to gray at once ("everything flashes white"). Without it, a reassigned cell keeps its frame and dissolves to the new source, so only the changed tile fades. Tradeoff (accepted): a fast scroll can briefly show a tile's previous thumbnail before the dissolve — don't re-add `recyclingKey` to "fix" it. For the same reason the grid tile's retry-remount `key` is the **reload nonce only, never the asset id** (an id-keyed element remounts+blanks every recycled cell). The viewer pager and filmstrip (`viewer.tsx`) are `FlatList`s (mount/unmount, not recycling; the filmstrip is **windowed** so a dense area's hundreds of thumbs don't all fire PHImageManager requests at open), so they leave `recyclingKey` off too — there it would only add a reset-to-blank flash. The filmstrip opens centered via **`contentOffset` + `initialScrollIndex` together** (`lib/filmstrip-layout.ts`): contentOffset alone positions the scroll but VirtualizedList's initial *render region* is `[initialScrollIndex ?? 0, +initialNumToRender)`, so a deep open lands on unrendered cells — a blank strip; with contentOffset set the list skips its own initialScrollIndex scroll, so the two compose.

### Metadata platform quirks (where bugs hide)
`hooks/use-asset-metadata.ts` is layered caches (full / location / time / iCloud) with in-flight dedup. Watch for:
- Android MediaStore returns `creationTime` `0` for photos with no DATE_TAKEN — use `firstValidTime` (rejects `0`/null), never `??`, then fall back to modification time. This caused blank dates.
- iOS photos may be iCloud-resident (`getIsInCloud`); rendering them needs a network download. Pass `asset.id` (a `ph://` URI) to `expo-image`/`expo-video`, never a resolved file path, or iCloud downloads fail silently.
- **Never probe iCloud residency on a VIDEO.** `getIsInCloud`'s iOS video branch (`Asset.swift`) calls `PHImageManager.requestAVAsset(forVideo:)`, which spins up the CoreMedia/AVPlayer pipeline (`PlayerRemoteXPC`/`FigPlayerInterstitial`/`FIGSANDBOX`) *per call*. The always-mounted Camera Roll feed probes residency in loops (entry selection + every shuffle refill + old-memory, all via `loadAssetIsInCloud`); on a heavily iCloud-offloaded library that's dozens of probes, and the repeated AVAsset instantiation floods `mediaserverd` and **crashes only in distribution (TestFlight) with no memory warning and no crash log** — a CoreMedia fault, suppressed under a debugger so it never repros in dev (don't chase it as OOM). Any PhotoKit access to a video's content touches AVFoundation, so there's no cheap probe: `loadAssetIsInCloud` (`use-asset-metadata.ts`) **short-circuits videos** via a cheap `getMediaType()` and treats them as in-cloud (feed never opens its entry on a video, rate-limits them in shuffle; Near Me grid/viewer are unaffected — they never call this). Only a **confirmed IMAGE** reaches the native probe: an `UNKNOWN` type (the read timed out/threw — a cold Photos framework, i.e. launch, exactly when the entry loop probes hardest) may still be a video, so it returns in-cloud **uncached**. Don't re-add a video residency probe.
- Screenshots are rejected differently per platform (subtype check on iOS, "Screenshots" album on Android) in `use-asset-feed.ts`.
- **Never cache a *failed* native read** (don't `.catch(() => null)` then `cappedSet`). A thrown read must propagate uncached so it can be retried; only cache a *successful* read (including a legit `null`, e.g. a no-GPS photo). `hydrateAsset` resolves each read into an `{ok}` result — **including the `getModificationTime` date fallback** (a timed-out fallback once cached `creationTime: null` = a session-long blank date) — and caches only when all succeeded; `useAssetMetadata` retries the best-effort meta on a capped backoff (~18s total — the old ~4s window ended inside the very warm-fan-out contention bursts that caused the failures, leaving readable photos captionless until remount). It surfaces only a *complete* meta (`fullCache.has`), so the caption never fades in with a blank date. **The same rule covers `use-reverse-geocode.ts`:** a thrown `reverseGeocodeAsync` (Apple rate-limits + the warm fan-out bursts) must stay uncached or it blanks the place for every photo in that ~100m bucket all session — failures stamp `failedAt` (8s throttle) and the hook does 2 bounded 10s retries (behavior unit-tested via `prefetchReverseGeocode` + mocked geocoder).
- **The intermittent "blank caption on the first photo" was a React-Compiler reactivity bug, not a read failure.** `useAssetMetadata` reads `fullCache.get(asset.id)` *non-reactively* in render. When the feed's `warmAssetMetadata` populated `fullCache` *between* the card's first render (cache empty → returned null) and the card's effect running, the effect's old `if (fullCache.has(id)) return` early-returned without `setFetched`, nothing re-rendered, and the compiler kept serving the memoized stale `null` forever. Fix: the effect **always** runs `tryHydrate` (never short-circuits on a cache hit), so `setFetched` always fires and syncs `fetched` → memo invalidates → caption appears. **Don't read a module-level mutable cache directly in render and assume a later external write will show up** — drive the surfaced value through state.

### Crash-proofing (rollout hardening, 2026-07)
The June 30 TestFlight crash ("Near me caused crash", 8s uptime, iPhone 12, no log — likely jetsam) was the **warm-launch collision**: the GPS fix lands at `LOCATION_FIX_MS` (8s) → first Near Me snapshot fans out ~a dozen `ph://` grid decodes, while the located-index delta sweep runs 8-wide with synchronous full-index checkpoint stringifies (fresh installs are immune: the grid can't populate until the first build completes). Mitigation: Near Me marks a **decode burst** (`lib/decode-burst.ts`, 10s latch, extended per snapshot adoption) → the sweep re-reads pacing **per batch** (`sweepPacing`: trickle 2-wide/150ms during a burst) and **defers checkpoints** (`canCheckpointNow`) until the burst closes. Crash telemetry: `lib/crash-log.ts` — ErrorUtils global handler (always delegates to the previous handler; never swallow fatals) + Hermes rejection tracker (**release only** — replacing it in dev kills LogBox), rotating 20-entry `crash-log.json` in the document dir with a breadcrumb ring; retrieve by **long-pressing the Settings sheet title** (shares the formatted log). Every root overlay in `_layout.tsx` is wrapped in `OverlayBoundary` (fails to **null**, one boundary per overlay so a thrower can't kill siblings, logs tagged) — except `OnboardingFlow`, which keeps the full-screen Reload fallback (failing to null would strand a new user on blank Paper). Persisted readers validate per-element/field: `parseAssetIndex` (drops corrupt elements AND strips their ids from `processedIds` so they re-locate), `parseNotificationSettings` (**present-null `placeCooldownMs` is the legit "Only once" and must survive validation**), `parseOnboardingState`, `parseDemoMode`.

## Conventions

- **Path aliases**: `@/*` → `src/*`, `@/assets/*` → `assets/*` (tsconfig + jest `moduleNameMapper`).
- **Tests** live in `__tests__/` dirs next to the code and cover **pure logic only** (clustering, cooldown, engagement, geofence selection math, time formatting). Heavy native/UI paths aren't unit-tested. Keep new logic extractable into pure functions for the same reason.
- **React Compiler is enabled** (`app.json` → `experiments.reactCompiler`). The `react-hooks/immutability` ESLint rule is deliberately **off** (see `eslint.config.js`) because every hit is a legitimate Reanimated `sharedValue.value` write — don't re-enable it.
- **SVGs import as components** via `react-native-svg-transformer` (`import Icon from '@/assets/icons/x.svg'`); see `metro.config.js` and `svg.d.ts`.
- **Web variants**: files like `use-color-scheme.web.ts` / `animated-icon.web.tsx` provide platform-specific implementations resolved by Metro.
- **Design system** is centralized in `constants/theme.ts`: light "gallery" look — `Paper` (white canvas), `Ink` (near-black text/borders), `DisplayFont` = `ArchivoExpanded-Black` (loaded at runtime in `_layout.tsx`; the `.ttf` must exist at `assets/fonts/`). Photos are framed to a fixed `PhotoRatio`. UI is **monochrome (Ink/Paper)** except one brand element: a persistent edge-to-edge spectrum gradient band under the top tab bar (`components/brand/spectrum-rule.tsx`, `BrandSpectrum` via already-linked `react-native-svg`). `Accent` (coral `#EE5D6C`) is a token but currently unused — the user reverted all other color to Ink; don't reintroduce it without asking. Loading states show the **Polaroid** (`components/brand/loading-polaroid.tsx` + `assets/images/polaroid.png`, cropped from the app-icon foreground) — pops up + breathes; used in the `_layout` boot gate and feed/Near Me cold-load. Native splash is polaroid-only (`app.json`, needs rebuild).
- **Commit messages**: short, lowercase, imperative, no conventional-commit prefix (e.g. "fix geofence re-enable and duplicate fires").
